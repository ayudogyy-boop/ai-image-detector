## 2.2.1：模型不可用与失败缓存恢复

用户在百度图片页遇到黄色“？”及“模型暂不可用”提示。旧提示不能区分图片读取、模型加载和推理失败，不能据此断言百度防盗链或某一种模型错误就是用户现场原因。审查确认并修复：

- 模型首次加载失败后不会再次初始化；现在实际推理请求可以按需重试，启动共享且尝试间隔至少 3 秒。运行时推理失败会释放 session，由后续请求重建；解码失败不重建健康模型。
- 元数据成功就把模型失败一起缓存十分钟；现在请求模型却没有有效模型结果时不写成功缓存。
- 无有效结果曾显示黄色“？”并使用占位 50 分；现在显示灰色“—”、空分数和独立未完成统计。详情给出阶段、HTTP 状态、截断并转义的具体错误与扩展版本。正常模型的 40/60 区间、未验签声明及可信来源签名优先级不变。

`npm run test:all` 共 186 项通过：57 元数据、18 工程回归、20 溯源/评分、3 对抗性、29 流水线、59 真机检查。实际 Chrome 故障注入覆盖首次模型下载失败、同一文档内恢复、403 状态、元数据成功但模型失败、重新悬停恢复与错误文本转义。

最终 `build/artifacts/ai-image-detector-v2.2.1.zip` 已解压到独立目录并装入 Chrome，上述 59 项真机检查再次全部通过。

基线 `results/current-color40-after-2026-11-10T13-18-33.json` 与 `results/current-recovery-2.2.1-2026-11-10T14-02-37.json` 的 240 张图片逐一核对：原始模型输出、展示分数、颜色、决策依据完全一致。AUC 0.6527、真图绿/黄/红 30/57/33、AI 图 9/58/53，均无推理错误；中位延迟 492ms（单次本机记录，不作为性能提升结论）。

最终 ZIP 在用户提供的百度页面实测，结果组中的一张真实图片显示红色 39 分，详情版本 2.2.1，模型状态 ready。现场记录为 `results/baidu-recovery-2.2.1-2026-11-10.json` 和同名 PNG。这只能证明本机独立 Chrome 环境的链路正常，不能替代用户原浏览器的具体错误诊断。

## 2026-11-10 用户指定颜色规则

当前模型展示分数固定为：**低于 40 红色、40–60（含边界）黄色、高于 60 绿色**。旧灵敏度设置不再改变区间；未验签声明不会覆盖已为红色的模型低分，没有模型结果仍弃权。可信 AI 来源签名依旧优先。

使用同一 240 张图片复测，未更换模型，原始模型输出逐图不变，AUC 仍为 0.6527：

| 指标 | 旧默认区间（红<29） | 当前区间（红<40） |
|---|---:|---:|
| 真图绿 / 黄 / 红 | 30 / 83 / 7 | 30 / 57 / 33 |
| AI 图绿 / 黄 / 红 | 9 / 94 / 17 | 9 / 58 / 53 |
| 真图红标率 | 5.83% | 27.50% |
| AI 漏为绿色 | 7.50% | 7.50% |
| 弃权率 | 73.75% | 47.92% |
| 明确结论准确率 | 74.60%（47/63） | 66.40%（83/125） |
| 中位延迟 | 500ms | 502ms |

这是按用户要求扩大红色区间的结果：检出与误报均增加，不能称为模型准确率提升。旧数据集不能代表现代生成器的识别能力。

结果保留在 `results/current-color40-before-2026-11-10T13-16-08.json` 和 `results/current-color40-after-2026-11-10T13-18-33.json`，均无推理错误。边界、未验签声明及旧设置兼容测试通过，`npm run test:all` 共 173 项通过（含 51 项真实 Chrome 检查）。最终 ZIP 的评分和设置文件与源文件一致；从 ZIP 加载的设置页已验证颜色说明和保存操作。

这个目录是 `ai-image-detector` 的**唯一事实来源**：任何改动检测逻辑的提交，都要能在这里跑出可对比的数字。
在它出现之前，项目里没有可用的评估集（`test-c2pa/` 的 6 个文件里 2 个是 14 字节的 404 文本、1 个是 Cloudflare 拦截页，剩下的 3 张全是真照片、没有一张 AI 图），所以「模型 74% 准确率」一直只是模型卡上的数字。

## 目录约定

```
eval/
├── README.md            # 本文件：约定、数据来源、局限
├── fetch-dataset.mjs    # 下载带标签图片 → data/（可重复执行，已存在的跳过）
├── models.json          # 候选模型登记表
├── fetch-model.mjs      # 下载候选 ONNX，并从各仓库 config 自动推导推理参数
├── harness.html         # 浏览器内推理页，支持可插拔模型
├── run-eval.mjs         # 评测驱动 + 指标计算 → results/
├── test-metadata.mjs    # src/shared/metadata.js 的单元测试
├── metadata-stats.mjs   # 统计评测集里的来源自述覆盖率
├── data/                # 下载的图片 + manifest.json   ← .gitignore，不入库
├── models/              # 下载的候选模型 + resolved.json ← .gitignore，不入库
└── results/             # 每次评测的 JSON 结果          ← .gitignore，不入库
```

约定：

- `data/` 和 `results/` **永不入库**，只保留脚本与文档。
- 每次评测产出一个带时间戳的 JSON，**不要覆盖历史结果**——否则无法比较改动前后。
- 改动检测逻辑时，先跑一次基线，改完再跑，用 JSON 里的数字说话。

## 怎么跑

```bash
cd ai-image-detector
node eval/fetch-dataset.mjs --per-class 120   # 下载约 240 张（只需跑一次）
node eval/fetch-model.mjs                     # 下载候选模型（只需跑一次）
node eval/run-eval.mjs                        # 评测当前线上模型
node eval/run-eval.mjs --model all            # 评测全部候选并输出对比表
node eval/run-eval.mjs --limit 40             # 冒烟测试，每类 20 张
node eval/test-metadata.mjs                   # 元数据解析与判定单测（纯 Node，57 项）
node --test eval/test-regressions.mjs eval/test-provenance.mjs eval/test-adversarial.mjs # 工程、溯源与对抗性回归
node eval/test-metadata-pipeline.mjs          # 流水线测试：Node + 真实浏览器各跑一遍（29 项）
node eval/test-extension.mjs                  # 真机端到端：把扩展装进 Chrome 跑 59 项检查
node eval/metadata-stats.mjs                  # 来源自述覆盖率统计
```

也可以直接用 npm 脚本：`npm run test`（单测 + 流水线）、`npm run test:ext`（真机端到端）、
`npm run eval`、`npm run build`。

依赖：先在项目根目录运行 `npm ci`，再使用系统 Google Chrome（可通过 `CHROME_PATH` 指定）。
单测和端到端测试不依赖 `eval/data/`；只有离线评测和覆盖率统计需要下载数据集。

## 2026-09-21 首轮评测的实测结论

| 模型 | AUC | 最优阈值准确率 | 真图误判 | AI 漏判 | 中位延迟 |
|---|---|---|---|---|---|
| current（线上，10.6MB） | 0.6527 | 61.3% | 5.8% | 7.5% | 366ms |
| smogy（57MB） | **0.8275** | 77.1% | **35.0%** | 15.0% | 1860ms |
| aid-vit（54MB） | 0.6626 | 67.1% | **71.7%** | 0.0% | 1917ms |
| deepfake-v2（54MB） | 0.5112 | 54.6% | 48.3% | 0.8% | 1908ms |

- **线上模型 5.8% 的低误报是「弃权」换来的**：它对 73.8% 的图不给结论。真正的能力指标是 AUC 0.653。
- **smogy 排序能力明显更强，但 28.3% 的真图拿到 p>0.99**（高置信误判），直接换用会把大量真实照片标红。
- **aid-vit 的 71.7% 误报**正是 CLAUDE.md 里「strong AI bias」的量化版本。
- **deepfake-v2 AUC 0.51 = 瞎猜**（它是换脸检测，不是生成图像检测，任务不对）。
- 候选模型都大 5 倍、慢 5 倍（1.9s vs 0.37s），**不适合 hover 交互**。

## 2026-10-19 量化档位实验：结论是「不是量化的问题」

模型卡自称 74% 准确率，本机实测只有 61.3%。一个自然的怀疑是 **Q4 量化吃掉了精度**。
线上跑的正是 `model_q4.onnx`，而模型卡的 74% 是 fp32 的成绩。于是把同一个模型的四个量化档位
全跑了一遍（`current-*` 系列，n=240，同一份评测流程）：

| 档位 | 体积 | AUC | 最优阈值准确率 | 真图误判 | AI 漏判 | 明确结论准确率 | 中位延迟 |
|---|---|---|---|---|---|---|---|
| Q4（线上） | 10.6MB | 0.6527 | 61.3% | 5.8% | 7.5% | 75.4% | 379ms |
| q4f16 | 8.9MB | 0.6527 | 61.3% | 5.8% | 7.5% | 75.4% | 397ms |
| fp16 | 29MB | 0.6511 | 61.3% | 5.8% | 8.3% | 74.6% | 364ms |
| int8 | 15MB | 0.6501 | 61.3% | 5.8% | 9.2% | 73.5% | 254ms |
| fp32 | 58MB | 0.6510 | 61.3% | 5.8% | 8.3% | 74.6% | 337ms |

**结论：四档量化的 AUC 差异在 0.003 以内（≈噪声），最优阈值准确率五档全是 61.3%。**
- 量化损耗不是 74% → 61% 的原因；这个差距只能来自**评测数据与模型训练数据的分布差异**。
- 因此**没有理由为了精度换更大的量化档位**：Q4 已经拿到了这个模型的全部能力，而且体积最小。
- 附带发现：`fp16` 在 ORT-web 1.27 的 `graphOptimizationLevel:'all'` 下**无法加载**
  （`SimplifiedLayerNormFusion` 找不到 `InsertedPrecisionFreeCast` 的输入名），必须在 `basic` 下才能跑；
  `q4f16` 同样需要 `basic`。`run-eval.mjs` 现在会自动逐级降级重试并记录实际使用的级别——
  也就是说，换成 fp16 不是"改个文件"就能上，还要接受图优化降级带来的性能损失。
- `int8` 反而最快（254ms）但体积大 40%；考虑到精度无差，**保持 Q4 是最优解**。

这个实验的意义：**把"换更好的量化"这条路关掉了。** 想提升能力只有两条路——换模型，或者不做视觉检测。

## 评估集已知问题（做发布决策前必须解决）

抽查被判为「高置信误报」的真图后发现，`RealArt` 类**混杂了大量非摄影内容**：

- 黑白三拼贴摄影作品（Zanele Muholi）
- 数字绘画 / 插画
- 重度修图的图库照（Shutterstock / Adobe Stock）

模型训练目标是「Midjourney 类图像 vs Google Open Images」，而这里的 real 类分布明显不同。
**所以本评测集的绝对误报率被高估，只有「同一批数据上的模型相对排序」是可信的。**
要做发布决策，需要把 real 类换成真正的相机照片，AI 类补上 2024+ 的生成器。

## 来源自述覆盖率（metadata-stats.mjs）

2026-11-10 用生产判定函数重新统计：240 张中 AI 图 **1.7%**（2/120）包含可识别的 AI 来源自述，真实图 **0%**。旧统计把普通软件字段、相机 EXIF 和未知 C2PA 一并计入，得到真实图 7.5%；这些不等于确定性证据，旧口径已修正。2.2 将这些字段明确降级为未验签自述，不能把这项统计称为已验证水印检出率。
**但这不能说明元数据层没用**——这批图在入数据集时已被剥掉元数据（AI 组只有 3 张 PNG 带文本块，其余 PNG 也可能含独立 XMP）。
要评估元数据层，需要一组**保留元数据**的样本：直接从 SD/ComfyUI/Firefly 导出的原图，或项目自带的 `test-c2pa/`。

## 评测复刻了什么

为了让数字代表**线上插件的真实行为**而不是某种近似，评测台尽量复用生产代码而不是复制它
（2026-10 审查发现：分数映射与融合以前是 content.js 的复制品，且已经落后于线上，于是"评测数字"和"用户看到的行为"是两回事；现已改为共享模块）：

| 环节 | 做法 |
|---|---|
| 预处理 | 真实浏览器 `createImageBitmap` + `OffscreenCanvas(224,224)` + `drawImage`，与 `offscreen.js` 的 `runInference` 逐行一致（缩放核会显著影响 AI 检测特征，自己写 resize 会有偏差） |
| 推理 | 同一个 `models/detector.onnx`、同一个 `lib/ort.wasm.min.js`、同样 `numThreads = 1` |
| 类别顺序 | `id2label = {"0":"fake","1":"real"}`，已从模型原始 `config.json` 核实 |
| 分数映射 | 直接 `require('../src/shared/scoring.js')` —— **与 content script 用的是同一个文件** |
| 融合 | 同上，`AIDScoring.scoreAnalysis`；验签/自述/模型分层，未验证相机与缺失 C2PA 不加权 |
| 元数据与判定 | 直接 `require('../src/shared/metadata.js')`，浏览器复用 `summarizeBytesAsync` 和 `AIDC2PA.verify` 处理完整资产，再用 `scoreAnalysis` 判定 |

## 指标怎么读

- **AUC**：原始模型把 AI 图排在真图前面的能力，0.5 = 瞎猜。这是视觉信号的**天花板**。
- **最优阈值准确率**：在自建数据上事后调出来的最好成绩。当前模型颜色按用户指定的固定区间（红<40 / 黄40–60 / 绿>60）显示；阈值变化不等于模型能力改善。
- **误报率（真图→红）**：这个插件最容易挨骂的地方。
- **漏报率（AI图→绿）**：虚假安全感。
- **黄色占比**：插件最常见的输出其实是不确定，要正视这一点。
- **明确结论准确率**：只在给出红/绿的样本里算。样本量小，别单独引用。

## 已知局限（改结论前务必先读这段）

1. **生成器年代偏老**：本数据集是 2022–2023 年的 Midjourney v4 / SD 1.x 作品，和模型训练集同源。**因此这里的成绩偏乐观，不代表 2025+ 的 Flux / GPT-Image / Seedream。**
2. **没有生成器标签**：只能算总体指标，无法看出「哪家生成器最容易漏」。
3. **真图偏影棚/图库**：真实类多为修过图的图库照片，属于「难负样本」。
4. **确定性层在这批数据上覆盖率极低**：数据集图片的元数据大多已被剥掉（AI 组只有 1.7% 命中），所以这张表主要反映视觉模型的能力；元数据层的能力需要用保留元数据的样本单独评估。
5. **视觉信号依然是天花板**：量化实验证明四档精度无差异，换量化不能改善 AUC 0.65。
6. **样本量**：每类 120 张时，AUC 的标准误约 ±0.03。别把 0.02 的差异当结论。
